# RUNBOOK — Guestbook Capstone

Аварийная инструкция для человека, который поддерживает Guestbook Capstone (FastAPI + PostgreSQL + Docker Compose).

**Где выполнять команды:** в терминале PowerShell, из корня клонированного репозитория `guestbook-capstone`, где находится `compose.yaml`. Docker Desktop должен быть запущен, а файл `.env` — настроен. В примерах используется локальный адрес `http://localhost:8000`; при развёртывании на сервере замените его на фактический адрес.

**Важно:** не публикуйте `.env`, пароли, токены и полные строки подключения. Не выполняйте `docker compose down -v` — этот флаг удаляет том PostgreSQL вместе с данными.

## 1. Сервис не отвечает

**Симптом:** `GET /` или `GET /health` не отвечает; браузер показывает ошибку соединения или ответ сервера с ошибкой.

### Диагностика — выполняйте по порядку

1. Проверьте доступность API:
   ```powershell
   curl.exe -i http://localhost:8000/health
   ```
2. Посмотрите состояние контейнеров `app` и `db`:
   ```powershell
   docker compose ps
   ```
3. Посмотрите последние ошибки приложения:
   ```powershell
   docker compose logs --tail=50 app
   ```
4. Проверьте сообщения PostgreSQL:
   ```powershell
   docker compose logs --tail=50 db
   ```

### Действия

- Если контейнеры не запущены, поднимите стек:
  ```powershell
  docker compose up -d
  ```
- Если `db` не готова или приложение сообщает об ошибке подключения, перейдите к разделу [«База недоступна»](#2-база-недоступна).
- Если контейнеры запущены, но `app` не отвечает, после просмотра логов перезапустите приложение:
  ```powershell
  docker compose restart app
  ```
- Проверьте восстановление:
  ```powershell
  curl.exe -i http://localhost:8000/health
  curl.exe -i http://localhost:8000/messages
  ```
  Ожидается HTTP `200`, для `/health` — `{"status":"ok"}`. Проверка `/messages` дополнительно обращается к базе.

**Откат:** если проблема началась сразу после релиза, выполните процедуру [«Откат версии»](#3-откат-версии).

**Эскалация:** если за 15 минут сервис не восстановился, передайте владельцу проекта результаты `docker compose ps`, последние ошибки из логов и текущий тег приложения (не прикладывая секреты). Контакт или канал связи должен быть согласован заранее.

## 2. База недоступна

**Симптом:** запрос `GET /messages` возвращает ошибку или не отвечает, хотя `GET /health` может возвращать `200`.

> В текущем приложении **нет** эндпоинта `/db-check`. `/health` не проверяет соединение с PostgreSQL. Для проверки связи приложения с базой используйте `/messages`.

### Диагностика — выполняйте по порядку

1. Проверьте запрос, использующий PostgreSQL:
   ```powershell
   curl.exe -i http://localhost:8000/messages
   ```
2. Проверьте статус контейнера базы:
   ```powershell
   docker compose ps
   ```
3. Посмотрите ошибки PostgreSQL:
   ```powershell
   docker compose logs --tail=50 db
   ```
4. Проверьте, принимает ли PostgreSQL подключения (команда выполнится, если контейнер `db` запущен):
   ```powershell
   docker compose exec -T db pg_isready -U guestbook -d guestbook
   ```

### Действия

- Если `db` остановлена, запустите её и дождитесь статуса `healthy`:
  ```powershell
  docker compose up -d db
  docker compose ps
  ```
- После восстановления базы запустите или пересоздайте приложение при необходимости:
  ```powershell
  docker compose up -d app
  ```
- Проверьте выполнение SQL-запроса непосредственно в PostgreSQL:
  ```powershell
  docker compose exec -T db psql -U guestbook -d guestbook -c "SELECT 1;"
  ```
- Проверьте путь от приложения до базы:
  ```powershell
  curl.exe -i http://localhost:8000/messages
  ```
  Ожидается HTTP `200` и JSON-массив сообщений (в том числе пустой `[]`).

**Эскалация:** если база не становится `healthy`, в логах есть признаки повреждения данных или ошибки авторизации, либо проблема не устранена за 15 минут, сообщите владельцу проекта. Не удаляйте том `pgdata` и не пересоздавайте базу «с нуля».

## 3. Откат версии

**Когда применять:** сразу после релиза возникли ошибки, и требуется вернуть ранее работавшую версию кода.

**Предусловие:** в GHCR доступны образы `ghcr.io/mira973/guestbook-capstone:v1.1.0` и `:v1.0.0`.

1. Откройте `compose.yaml` и в секции `app` укажите предыдущую версию:
   ```yaml
   app:
     image: ghcr.io/mira973/guestbook-capstone:v1.0.0
   ```
   Сохраните существующие `ports`, `environment` и `depends_on`. **Удалите или закомментируйте `build: .`**, если он присутствует: для отката нужно использовать опубликованный образ, а не локальную сборку.
2. Скачайте версионированный образ и примените конфигурацию:
   ```powershell
   docker compose pull app
   docker compose up -d
   ```
3. Проверьте состояние и ответы сервиса:
   ```powershell
   docker compose ps
   curl.exe -i http://localhost:8000/health
   curl.exe -i http://localhost:8000/
   curl.exe -i http://localhost:8000/messages
   ```
   Для `v1.0.0` в ответе `/` **нет** поля `version`; `/health` должен вернуть `{"status":"ok"}`. Успешный ответ `/messages` подтверждает работу с сохранённой базой.
4. Зафиксируйте в описании инцидента время, исходный и конечный теги, причину отката и результат проверок.

**Ограничение:** меняется только образ приложения. PostgreSQL и его постоянный том остаются прежними. Откат кода **не откатывает схему или данные БД**; при ломающей миграции прежняя версия может не работать. Перед релизом изменения схемы должны быть обратно совместимыми.

**Важно о простое:** текущий стек Docker Compose использует один экземпляр `app`; пересоздание контейнера может вызвать краткий перерыв в обслуживании. Это не rolling deployment без простоя.

## 4. Полезные команды

```powershell
docker compose ps                   # состояние контейнеров
docker compose logs --tail=50 app   # последние логи приложения
docker compose logs --tail=50 db    # последние логи PostgreSQL
docker compose up -d                # поднять стек без удаления томов
docker compose restart app          # перезапустить только приложение
```
